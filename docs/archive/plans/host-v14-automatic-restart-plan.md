## 1. 目标与授权范围

用户点击一次“重新启动 Host…”或“重启并应用更改…”，Host 先按现有规则处理未保存文档，再正常关闭当前会话，由轻量助手等待旧进程退出后启动新的 Host。新进程重新读取已保存的插件开关及其他启动配置，用户无需手动再次打开程序。

采用真实进程重启。窗口会短暂关闭再出现；不在当前进程重建 Avalonia App、HostRuntime 或插件加载上下文，也不将关闭全部 Document 称为完整重启。

本文保留实施设计与验收目标。初次方案文档提交为 `3cff108523ad`；本轮从该干净基线直接在 master 实施。实际类名、阶段交付与取舍见开发记录，现行行为以[自动重启契约](../../reference/host-restart.md)为准。

### 1.1 必须满足的约束

- SOLID 是首要规定；设计模式朴素使用，以职责清楚、状态所有权明确和可验证为准。
- 新增及实质修改的核心代码使用详细中文注释，解释设计思路、提交点、取消和失败边界。
- 单元、生命周期集成、Headless UI、真实子进程交接及本地开发门禁完整覆盖；测试必须证明行为，不能只验证调用次数或文案。
- 同步受影响的当前文档，并按既有惯例维护专用验证文档、开发记录与最终 JSON 证据。
- 不使用 AIFLOW，不读取、生成或维护 `.aiflow` 流程上下文。
- 不使用 Windows CI，不执行 `seal`、发布 Windows Smoke、发布覆盖率或发布重复性门禁；不修改这些发布规则。实际发布时另行使用发布门禁。
- 本轮开发门禁为本地专项测试及现有完整 `verify`。本机 Windows 上的开发测试和手工验证不等于 Windows CI 或发布验收。
- 直接在 `master` 按阶段提交，不新建分支、不重写已有历史。只提交本任务修改；若实施时存在其他修改，先记录并保留。
- 不部署安装目录、不上传包、不打发布标签，不修改外部业务插件。

### 1.2 不包含的能力

不包含进程内热加载、DLL 自动替换、在线更新、崩溃自动拉起、后台守护、定时重启、Document 跨进程自动重开、后台业务任务续跑或通用插件管理框架。原生后台任务的收尾仍由现有插件生命周期负责。

## 2. SOLID 与中文注释规定

| 原则 | 本方案约束 |
| --- | --- |
| SRP | 重启协调器只管理一次用户请求；关闭准备仍归工作区与布局；资源释放仍归 HostRuntimeShutdown；启动信息解析与进程操作分别承担确定性规则和系统副作用；助手只处理交接 |
| OCP | 菜单和看板共用一个内部用例；新增入口不复制退出流程；启动形式差异集中在启动信息解析处，不散落到 ViewModel |
| LSP | 普通退出、保存确认、布局失败及资源保留语义不退化；生产进程端口与测试替身保持相同取消、超时和失败语义 |
| ISP | UI 只获得请求重启与读取忙碌状态的窄端口；进程端口只提供实际需要的启动、等待与交接能力；不暴露容器或任意脚本执行 |
| DIP | UI 和协调逻辑不直接调用 Process.Start；组合根显式注入依赖；释放完成后的进程交接不再解析已释放的 Provider |

使用普通 `sealed` 类、不可变记录、少量窄接口和显式方法调用。只在系统副作用、生命周期或真实替换边界引入接口。不使用通用中介者、事件总线、状态机库、策略插件系统、反射注册或泛型事务框架。

中文注释要求：

1. 类型 XML 注释说明用途、状态所有者、依赖方向和释放责任。
2. 关键方法说明 UI 线程要求、幂等性、取消语义、返回结果及可恢复范围。
3. 明确解释为什么“窗口关闭”“PID 消失”“Process.Start 返回”都不能单独证明重启成功。
4. 注释写清准备阶段可撤销、窗口最终关闭后不可承诺恢复原实例；已成功保存的业务文件不会因取消重启而撤销。
5. 对命令排空、自身命令租约、设置保存竞态、助手确认、晚到回调、超时及资源保留分支说明设计思路，并映射到专项测试。
6. 不逐句翻译代码；注释必须与实现和实际测试一起更新。

## 4. 用户行为契约

### 4.1 入口与展示

- 主菜单提供“重新启动 Host…”，无插件开关变化时也可使用。
- 插件看板存在已保存且待生效的修改时提供“重启并应用更改…”，含义是应用全部已保存的启动设置，不仅是当前选中插件。
- 两个入口共用一次重启协调状态；准备期间禁用重复请求并显示“正在准备重启”。
- 提示“重启将关闭所有文档，未保存内容会先询问”。默认不增加与既有保存确认重复的通用确认框，不增加快捷键。
- 保存未完成、其他关闭流程占用或窗口尚不可用时给出原因，不能静默丢弃请求或假装已经重启。

### 4.2 关闭准备与撤销

1. 先验证本次启动方式可重建，再接受一次重启请求。不可支持的启动方式应在拆除 UI 前明确反馈。
2. 在插件设置服务层暂缓新写入，等待此前已接受的保存或重读完成；失败时反馈并取消重启，不把未保存意图当成已提交设置。所有入口遵守同一保护，取消后恢复写入能力。
3. 复用现有整窗关闭准备，汇总保存/放弃/取消决定，等待文档命令排空并复查修改版本；冻结并最终保存布局。
4. 准备期间禁止新增文档和与退出冲突的操作；使用可撤销的现有关闭许可，不提前调用不可逆的 Runtime BeginShutdown。
5. 所有准备成功后建立助手交接并取得就绪确认；失败则撤销许可、恢复布局调度和交互。
6. 进入原生最终关闭路径。即使准备成功，最终 Closing 拒绝也必须撤销本次助手及重启意图。

取消或准备失败时，保留尚未关闭的原 Document、Tool、View 和 Scope，不逐个提前拆除。准备期间用户已经成功保存的文件保留其保存结果，不提供文件事务回滚。最终关闭后则不能宣称恢复原工作区。

### 4.3 重启后的状态

| 状态 | 行为 |
| --- | --- |
| 插件启用策略 | 新 Host 按磁盘中的已保存配置重新发现并加载；启用不承诺插件初始化一定成功 |
| 工具布局、显隐、收藏、偏好 | 沿用当前持久化和恢复规则；缺失或禁用工具仍按既有规则保留记录 |
| Document | 当前文档全部关闭；新 Host 不自动重开、不自动创建文档恢复清单 |
| 用户文件与插件业务数据 | 不删除、不迁移、不改变路径或格式 |
| 后台任务 | 按已有退出协议收尾；不把重启等同于任务自动续跑 |
| 普通退出 | 没有有效重启请求时只退出，不启动助手或新 Host |

外部实例仍可能修改同一数据根的配置；本功能不提供跨整个重启过程的全局配置事务。新 Host 使用实际启动时读到的有效设置，不覆盖他人的已保存修改。

## 5. 最小内部设计

以下名称用于分配职责，不要求机械地一项建立一个接口或文件；实现时按已有结构收敛。

| 组件 | 职责与寿命 |
| --- | --- |
| HostRestartCoordinator / IHostRestartActions | UI 可访问的窄用例，拥有单次请求、忙碌状态和准备结果；调用既有关闭准备，不负责资源 Dispose 或启动命令拼接 |
| HostLaunchSpecification / HostLaunchResolver | 冻结并验证可执行路径、必要入口 DLL、参数、工作目录与有效数据根；普通记录和纯规则优先 |
| RestartHandoffSession | 本次助手连接、就绪/撤销/清理完成信号及超时的所有者；由进程入口持有，寿命长于 Runtime，不捕获插件、View 或 Provider |
| 系统进程适配器 | 启动助手/Host、保留目标进程身份、等待退出；把操作系统副作用隔离为可测试端口 |
| RestartHelperRunner | 无插件的助手入口；确认目标旧进程和本次会话，等待批准与退出，然后至多启动一次新 Host |
| 既有关闭与布局对象 | 继续拥有保存确认、许可、布局冻结及撤销；必要时只提取实际共用的窄方法，不扩展为通用应用管理框架 |

重启命令只登记请求并安排受观察的后续 UI 工作，释放自身命令租约后再进入最终关闭和排空。不能让 Handler 等待整个进程退出，也不能使用未观察异常的任意后台任务。协调器负责跟踪准备任务、取消和错误，菜单与看板共用结果。

## 6. 进程交接协议

### 6.1 助手入口与启动信息

优先复用同一个可执行程序的内部助手模式；在正常诊断会话、HostRuntime 和 Avalonia 主应用创建之前分流。助手正常等待时不加载插件、不读取或锁定工作区配置、不创建主窗口、不显示控制台窗口。

启动规则集中处理：

- 覆盖 Windows x64 的正常 apphost 启动及 `dotnet <Host.dll>` 启动；`dotnet run` 启动的应用按实际进程形态解析，不重新执行构建命令。
- 自包含/单文件按实际可执行路径处理，不依赖单文件场景可能缺失的程序集 Location。开发验证使用本地构建及已有可用样本，不为本功能触发发布或部署。
- 使用结构化参数列表，不拼接 shell 命令；路径包含中文、空格及引号边界必须经过测试。
- 保留有效工作目录、必要用户参数和已解析的数据根。环境变量继承规则显式定义；内部助手参数、一次性交接信息和测试探针标志不传给普通新 Host。
- 不把内部重启标记写入长期设置；新 Host 默认是普通启动，不能自动请求再次重启。
- 目标必须是本次 Host 的启动身份，不提供任意程序或脚本执行入口。未知启动形式在关闭准备前失败。

### 6.2 一次性交接与两个必要条件

采用每次请求独立的本地进程间通道，例如受当前用户限制的命名管道，传递最少的版本化消息。通道与本次随机会话身份绑定，设长度和超时边界；标记不得写入日志或由下次普通启动扫描复用。不要为了几个消息建立通用 IPC 框架。

助手在回报 Ready 前取得目标旧进程的稳定等待对象，并核对进程身份；不能只保存 PID、延时后再按 PID 猜测同一进程。建立连接时旧进程已不存在、身份不符或协议不完整，均拒绝拉起。

固定交接顺序：

1. 旧 Host 完成可撤销的文档、设置及布局准备。
2. 启动助手，助手连接并证明可以等待本次旧进程，回报 Ready。
3. 旧 Host 请求最终关闭；若被拒绝，发送 Abort 并解除本次请求。
4. 主窗口和相关浮窗关闭，消息循环返回；Program 沿原所有权顺序完成 Runtime 及正常退出资源清理，并检查结构化结果。
5. 只有清理成功才发送 CleanExitReady，助手确认收到；旧 Host 不等待新 Host 启动，继续正常退出。交接对象不能随 DI 容器提前释放。
6. 助手同时满足“本次 CleanExitReady 有效”和“已取得的旧进程确实以成功状态退出”，才启动一次新 Host。
7. 新进程正常走既有启动链；助手释放句柄及通道后退出。

Ready 只是“助手可用”，不是启动新 Host 的许可；CleanExitReady 也不能越过等待旧进程退出。旧进程崩溃、被强杀或单纯退出码为 0 都不能代替完整交接。准备成功、清理完成和新 Host 初始化成功应在记录中分别表达。

最终日志关闭、退出码确定与 CleanExitReady 的关系在 P1 明确：不能在仍可能发生影响退出成功的清理之前发送最终许可。程序级捕获保持失败退出码，并保留原始清理诊断；不把启动失败回滚误当成正常重启退出。

### 6.3 失败边界

| 失败位置 | 必需行为 |
| --- | --- |
| 保存、布局、启动信息或助手 Ready 失败 | 撤销准备，保留工作区并显示原因；不存在可触发未来重启的残留意图 |
| 最终原生关闭拒绝 | 撤销所有许可及助手，普通退出也不能消费本次请求 |
| 资源保留、排空超时、插件 Shutdown 或 Provider.Dispose 失败 | 不发送 CleanExitReady，不自动拉起；记录具体失败。若窗口已经关闭，不承诺重建原会话 |
| 通道断开、父进程异常退出、协议不符 | 默认不启动；助手限时结束，不能退化为只看 PID 或固定等待时间 |
| CleanExitReady 后旧进程迟迟未结束 | 限时终止本次接力，反馈失败，不强杀旧 Host、不提前拉起新实例 |
| 新进程创建失败 | 助手提供独立中文错误反馈及诊断位置；不用已释放的旧窗口，不无限重试 |
| 新 Host 自身初始化失败 | 沿用既有启动失败界面；不自动重启循环，也不误报插件均已成功加载 |

助手失败后的可见反馈可复用无插件的最小错误界面，只在确有错误时创建；不能为了反馈再次启动完整 Host。各阶段超时使用现有时间抽象或可注入时间源，具体有限值在实现时记录并覆盖测试，不用固定 sleep 推测关闭完成。

每阶段先补有行为价值的失败/取消测试，再接入实现；完成后按可审阅单位提交到 `master`。只修改本功能必要路径；超出范围的旧缺陷单独记录。不为了绿色结果削弱断言、跳过矩阵、清理 API 基线或修改发布政策。

## 9. 完成判定

- 两个入口均完成一次真实进程重启，普通退出不重启，连续点击只接受一次。
- 保存/布局/最终关闭拒绝可以取消；取消不提前释放工作区，已保存文件不撤销。
- 只有正常清理成功且旧进程真正退出后才拉起新 Host；自等待死锁、资源保留误判、助手残留和重启循环有测试证明。
- 新进程正确采用保存后的插件开关及原数据根，工具按既有规则恢复，Document 不自动重开。
- 专用矩阵全部必需自动化实际运行；缺测试、零命中、缺证据、跳过或失败不能标为通过；最终完整本地 verify 成功。
- SOLID 与详细中文注释人工审查完成，当前文档和开发记录同步；真实桌面未执行项明确留待验收。
- 开发实现、自动验证、人工验收、部署、公开发布分别记录；V14 开发通过不授予发布资格。
