> 用途：减少 Host 开发验证中的重复文件复制、重复交互和多处规则维护，提高失败反馈速度与证据可读性，同时保持有效行为覆盖。
> 状态：待实施；本次仅编写方案与专用验证计划。日期：2026-09-21。
> 调研基线：`83f7aeaad048874439d0133f5a4cb233cb14c081`，编写前工作树干净；实施前重新核对 HEAD、差异和实际测试输入。
> 配套：[V21 专用开发验证计划](host-v21-gate-and-test-efficiency-verification.md)。当前执行入口继续以[主仓验证](../maintenance/verification.md)和现行代码为准。

V21 是 Host 改造序号，不修改产品、程序集、SDK、NuGet 包、Document Envelope 或 Layout schema 的版本。下文区分已有审视事实与拟实施行为，不把历史通过记录算作 V21 实施结果。

## 1. 目标与首要规定

衡量优化是否成立，应同时回答：每项检查保护什么、谁负责准备和清理输入、同一规则需要维护几处、失败后能否直接定位原因，以及完整开发验证是否保留必要场景。文件数、测试总数和代码行数不作为压缩目标。

1. **SOLID 是首要规定。** 每项变更先说明职责、依赖和资源所有权；不能以提速或减少代码为由破坏隔离、取消、失败、原子提交及释放边界。
2. **设计模式朴素使用。** 优先现有具体协作者、普通方法、少量不可变记录和明确的顺序调用。不建立通用测试平台、DAG 调度器、策略注册框架、第二容器或以反射发现阶段的机制。
3. 新增或实质修改的核心类型、方法和关键分支使用**详细中文注释**。解释职责、输入输出、资源归属、时序、失败处理及设计理由，不逐行复述代码。
4. 单元测试、Plugin 集成回归、必要的 Headless UI、Gate 工具自测和完整本地开发 `verify` 必须齐全。每项要求落实到真实断言或明确审查证据；测试类存在、数量不变或截图存在均不能代替覆盖证明。
5. 同步更新方案、专用验证、现行开发说明、内部设计说明及导航。方案、代码完成、自动验证、人工验收、部署和发布分别标记。
6. **不使用 AIFLOW**，不读取或维护其上下文、任务记录及更新候选。
7. **不使用 Windows CI 与发布门禁。** 开发阶段仅执行本机专项、工具自测和既有 `verify`；不执行 `seal`、发布 Windows Smoke、发布覆盖率或发布重复性门禁，不修改 CI、不部署安装目录、不上传包或创建发布标签。发布时再使用发布门禁，既有政策和阈值保持。

当前请求只授权形成文档。本次不修改生产代码、测试实现、Gate 或脚本，不把本方案写入已实现能力。

## 4. SOLID 与朴素设计的落实

| 原则 | 具体落实 | 避免的做法 |
| --- | --- | --- |
| SRP 单一职责 | 夹具准备输入，场景测试验证行为，UI 助手等待明确条件，Gate 编排，reader 解析证据 | 一个万能 TestContext 同时编译、复制、启动、点击、判断通过并发布报告 |
| OCP 开闭原则 | 新增场景使用显式测试数据和已有窄助手；阶段使用可直接阅读的定义 | 为假设中的更多平台/插件建立自动发现和可配置执行引擎 |
| LSP 里氏替换 | 优化夹具后仍执行同一启动、取消、退出和加载协议；小助手保持原有超时/失败含义 | 用模拟启动替代真实重启，用方法调用替代必须验证的鼠标/窗口事件 |
| ISP 接口隔离 | 等待、产物核对和证据读取各自接受所需参数；有真实替换点才引入接口 | 为每个小类配接口，或让全部测试依赖带大量开关的公共基类 |
| DIP 依赖倒置 | 复用现有进程/文件/UI 边界，以普通函数或窄输入注入可控条件 | 为测试向 SDK 或生产 ViewModel 增加入口，将 IServiceProvider 传入无关协作者 |

共享助手只承载重复机制，不包含被测业务的预期算法。测试必须独立表达期待的结果，避免生产代码和测试共用同一个判定从而一起出错。

## 5. P0：基线与逐项测试去向

实施开始时记录 HEAD、未提交差异身份、SDK、运行平台、补丁身份、实际命令、输入目录、缓存状态及后台负载。已有记录只用于选热点；对拟改热点做同机、同条件的实施前测量。

建立逐项去向表，至少包含：原测试全名与参数、保护的契约、所在层级、保留/迁移/合并理由、新测试全名与参数、验证矩阵编号、实际结果。一个旧测试可拆为多个职责明确的测试，多个重复断言也可合并，但每个有效行为都必须有去向。

计时只用于解释优化收益，不作为新的机器速度门槛。需要比较时，针对受影响热点固定输入各取三次样本，记录全部结果和中位数；失败样本单独解释，不能通过自动重试抹去。不反复执行完整 verify 充当微基准，最终完整开发验收单独执行一次，发现新变更或失败再按影响补跑。

## 6. P1：进程夹具的依赖与复制收敛

### 6.1 设计思路

先减少每次必须准备的字节和文件，再考虑复用。保留每例独立应用副本、Controls、数据根和故障注入；本轮不引入共享可写模板、硬链接树或跨测试全局应用目录。

### 6.2 处理步骤

1. 分析 RestartHarness 的构建文件、`.deps.json`、托管/原生依赖和平台目录，分别测量文件数量、字节数及夹具准备时间。
2. 优先取消测试副本中无运行用途的原生调试符号复制；托管 PDB 的诊断和可能的采集用途单独判断，不能按扩展名全部删除。
3. 核对按当前受支持运行平台生成最小可运行闭包的可行性。若采用 RID 构建，使用独立输出并补齐对应 restore 输入，不能向现有无 RID 输出直接塞入新全局属性造成写入冲突。
4. `.deps.json`、runtimeconfig、apphost、当前平台必要 native 文件、插件清单和托管依赖完整保留；不手改依赖描述来掩盖缺文件。
5. 复制清单应显式排除测试证据和以前的临时输出。构建增量复制必须能移除清单中已经退出的旧文件，不能仅增加 SkipUnchangedFiles 而留下旧依赖。
6. 只测得复制仍是主要成本时，再评估下一步；不在本阶段增加通用内容缓存。

验收继续覆盖 apphost / dotnet 两种启动形式、三次进程启停、插件禁用再启用、启动取消/失败/慢加载、无许可退出、强杀、错误退出、延迟退出及布局锁交接。应证明实际加载到正确补丁和测试插件，而不是仅检查文件数下降。

现有非目标平台路径不能被悄悄删掉或跳过；不支持的新组合明确报告适用限制，实验平台的支持范围不在 V21 中重新定义。

## 7. P2：UI 等待、测试分工和证据

### 7.1 等待有明确目标

区分三种操作：排空约定 Dispatcher 优先级、等待控件已完成布局、等待异步业务完成。优先复用现有完成 Task/事件和 TaskCompletionSource；确需观察 UI 条件时使用有界条件等待并在超时报告目标及最后状态。

鼠标、快捷键和窗口关闭动作只发送一次，不能在等待循环中重复点击，也不能捕获失败断言后持续重试直到偶然通过。负向竞态测试需要显式就绪/释放信号，不能用一次 Dispatcher flush 代替操作已经结束的证明。

提取少量同项目助手即可，不建立通用 UI 自动化 DSL。修正 TestAppBuilder 中与实际 Skia / UseHeadlessDrawing 配置不符的旧注释。是否拆分渲染进程/程序集留待测量，本轮默认保持当前渲染配置。

### 7.2 分工与重复轮次

| 层级 | 主要责任 |
| --- | --- |
| Unit | 保存/取消/失败决策、状态转换、查询、协议和边界的完整矩阵 |
| Plugin 集成 | DI、加载隔离、生命周期、真实文件与进程交接 |
| Headless 交互 | 控件绑定、按钮/菜单/快捷键接线、窗口事件、焦点和取消后继续操作 |
| Headless 布局 | 可见性、尺寸、单一父级、浮窗和视图回收所有权 |
| 像素验证 | 图标颜色、填充、裁剪等可稳定自动断言的画面属性 |

先确认各层保护的触发链，再调整测试。窗口事件否决与业务决策取消不是同一条件；主窗/浮窗、四个停靠方向、最后工具、跨窗口旧队列、保存中再次修改等不能凭名称相似合并。

多轮打开/关闭的寿命验证集中到明确场景，入口接线保留必要轮次；每次减少重复都写明额外轮次原来能捕获的错误及其新落点。最终清理前断言创建/释放次数、引用身份和视图位置，避免清理兜底掩盖泄漏。

### 7.3 截图与实际断言

界定截图为辅助证据或像素断言输入。没有期望值比较的截图不称为自动视觉通过；已有 IconRenderingUiTests 像素断言继续执行。

Gate 运行时将截图和进程附属证据归入本轮、套件、场景的独立目录，避免固定 `bin/TestResults/vXX-*` 被后续覆盖；单独 dotnet test 也有明确的本地输出位置。优先让现有证据出口共享一个可选目录约定，按场景区分文件名，不新增证据服务框架。没有启用截图导出时行为断言仍执行，必需的像素断言不能受导出开关影响。

## 8. P3：开发 Gate 编排与证据可靠性

### 8.1 简化内部表达并提前失败

- 保留现有 `verify` 默认完整验证。`--scope host/all` 可作为兼容参数接受，内部不再构造没有差异的执行分支；先查实际消费者再决定是否退役参数，错误参数仍明确失败。
- 单仓执行优先传递明确的源码根/快照；历史 summary 的 `sources.main`、scope 与源码身份语义保持，不为内部清理强制迁移外部记录。
- 顺序阶段使用一个可直接阅读的定义及具体方法，保留失败立即停止、阶段耗时和失败证据；重复阶段不能静默吞掉或执行两次，不继续维护仅证明旧去重容器实现的测试。
- 拟将开发 verify 的契约检查放到 build 与输出 DLL 验证之后、耗时测试之前。API 比较必须使用当前构建输出；补丁准备仍先于 restore。

目标开发顺序为：布局补丁 → Dock 补丁 → locked restore → Release build 与 DLL 身份 → contracts → tests → packages → package-acceptance。最终以实施后的唯一阶段定义为准，更新配置消费、测试、帮助与维护说明。

该顺序调整仅针对开发 verify；不得借共享编排改写 seal 发布顺序、重复性要求、发布资格计算或覆盖率规则。共享代码的边界可用纯工具单测和差异审查保护，不执行真实发布流程。

### 8.2 必需产物和 TRX

Dock 与 Avalonia DLL 都从明确的必需消费项目得到路径：应有而缺失立即失败；真正不引用对应依赖的项目按其职责排除，不能使用 Where(File.Exists) 猜测是否必需。哈希不符和缓存错配继续拒绝。

TRX 解析与通过政策分开：reader 读取/校验文件结构、必需字段、合法非负计数、结果明细和运行结果；Gate 判定完整成功。先核对现有 xUnit v2/v3 和 VSTest 真实输出的含义，不把 outcome 枚举、executed 定义或辅助计数作未经核实的假设。

至少拒绝：缺文件、坏 XML、缺失/重复关键节点、缺失或非法计数、零测试、失败/跳过/异常终止、计数与结果明细不一致，以及命令失败却留下局部 TRX。保持真实包验收必须恰好一项通过的现行约束，未来扩展另行评审。

### 8.3 套件证据

以一次解析得到的套件结果同时用于 Gate 判断和证据输出。记录套件 ID、源码/run 身份关联、命令和过滤器、进程退出码、TRX 路径及摘要、总数/执行/通过/失败/跳过与异常结果、进程墙钟时间和慢用例；区分 TRX 时间与命令总耗时。

优先在各 pass 增加独立套件证据文件，保持现有 schema 2 summary 的必需字段与含义；若需新增汇总字段，先核对读者兼容性。失败或尚未执行的套件明确标记，不把缺结果补成零或成功。附属目录使用相对路径关联，不另造一份通过判定算法。

Gate 自测仍独立执行，避免重建正在运行的 Gate。套件并行、增量测试选择器和发布前置检查均不作为本轮提速手段。

## 9. P4：重复单测与活动源码扫描

SDK 导出面由 SDK 边界测试负责，Host 不导出/不依赖旧总线由 Host 边界负责，实际调用行为由行为测试负责。先归并 IHostEventBus 等同一事实的重复断言，保留不同契约的独立断言。

源码规则限定为实际活动项目及必要模板目录，明确排除 artifacts、bin、obj、临时源克隆与外部仓库。新增活动项目仍应被规则覆盖，不能靠手写不再更新的固定项目清单漏检。使用受控目录输入验证扫描边界，不为单次整理新增全仓字符串零命中测试。

Vxx 测试名可在归并时按行为改名，历史映射保留；不为统一命名触碰所有测试文件。测试数量可以下降，但下降必须来自已解释的重复或迁移，不设置补齐旧总数的指标。
