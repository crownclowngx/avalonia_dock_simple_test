# 保存的不只是代码，还有继续使用的路径

## 要解决的问题

当一个低频能力暂时不再维护时，怎样让未来的自己或其他使用者仍能理解、构建、验证并继续演进它？

## 核心观点

将软件连同契约、数据语义、环境描述和验证依据共同保存。需求重新出现时，根据条件选择恢复旧环境、迁移、重写或替换。

## 关键公式

原文将软件基底定义为：

\[B=(H,K,P,D,E,V,L)\]

| 符号 | 需要保存的材料 |
|---|---|
| $H$ | 可运行 Host |
| $K$ | SDK、接口和行为契约 |
| $P$ | 插件或模块 |
| $D$ | 数据格式、样例和语义 |
| $E$ | 构建环境与依赖描述 |
| $V$ | 验证器和验收依据 |
| $L$ | 来源与许可信息 |

## 交互演示

点击“维护、归档、休眠、恢复、迁移、分叉”节点，查看每条路径需要的前提和材料。归档是维护状态的变化；恢复或迁移是否成功，仍需要重新验证。

## 适用边界

“可分叉软件基底”是工作术语。当前 Host 和插件机制提供可开展实验的基础，但尚未证明休眠多年的插件一定能够低成本恢复，也未证明 AI 可以普遍降低全部维护成本。
