## 2. 当前项目基线

### 2.1 已经具备的能力

当前代码已经形成基本下载链路，并非从零开始：

- 支持 BV、AV、普通视频链接、b23.tv 短链和番剧 EP/SS 解析。
- 支持单视频、多 P 和番剧分集选择。
- 支持画质、音频质量、输出目录和分组目录配置。
- 支持字幕、弹幕和封面下载。
- 支持多连接分块下载、CDN 回退和断点续传。
- 支持 ffmpeg 合并 DASH 音视频。
- 已有 SQLite 任务持久化和三阶段进度记录。
- 已有 `BiliDownloadCoordinator`，下载执行已开始脱离 Tool ViewModel。
- 已有启动后迁移运行中任务为“已中断”的基础逻辑。
- 已有全局开始、停止、失败重试、删除和打开文件位置功能。

### 2.2 当前工程状态

- `BiliDownloader.csproj` 当前可以构建通过，基线为 0 个错误。
- BiliDownloader 已有可独立运行的 xUnit 测试项目，G1 完成后共有 14 项插件测试。
- 下载协调器、登录状态、凭据、设置和任务存储由插件依赖注入容器统一管理。
- 插件初始化与有序关闭已脱离 Tool/Document 视觉树生命周期。
- 凭据与任务已经解耦；本地存储采用 Windows/Linux 共用的路径和加密抽象。

### 2.3 需要优先解决的问题

下列问题会直接影响长期使用，必须早于新内容源开发：

1. 单任务缺少独立暂停、继续、重来和取消能力。
2. 当前全局停止会影响所有活动任务，不能替代单任务控制。
3. 任务中心缺少搜索、筛选、多选和批量操作。
4. 高频进度写库仍有异步失序和异常未观察风险。
5. Document 只保存部分配置，不能完整复用下载方案。
6. 文件命名、文件冲突、磁盘空间和提交预检尚未形成统一流程。
7. ffmpeg 支持检测和手动选择，但缺少一键安装与修复。
8. Linux 全链路仍需继续处理 ffmpeg、打开文件位置、部署与发行包；G1 只完成数据安全基础的跨平台化。
9. 仍缺少真实网络与完整下载链路的集成回归基线。

## 3. 总体实施原则

后续开发必须遵守以下顺序和边界：

1. **先可靠，后扩展**：先完成任务控制、安全、恢复和测试，再增加新的内容源。
2. **Document 表达意图**：Document 保存来源、筛选、质量、命名、目录和冲突规则。
3. **Tool 管理执行**：Tool 负责全局任务展示、搜索、筛选和控制，不拥有下载线程。
4. **Coordinator 唯一调度**：所有提交和任务控制命令都由唯一 Coordinator 串行协调。
5. **SQLite 保存事实**：消息只负责通知，UI 必须能够从 SQLite 重新建立状态。
6. **启动不自动恢复**：历史任务只能由用户确认后继续，不得在启动时自动联网。
7. **批量场景优先**：设计和验收均以 100 个任务为基准，而不是只验证单任务。
8. **安全默认开启**：Cookie、签名 URL、请求头等敏感数据不得进入任务库、日志或导出文件。
9. **功能完成后再宣称**：只有通过验收的能力才可以在 `PRODUCT.md` 中标记为“已实现”。

**状态：已完成（2026-07-21，提前完成）**

主要工作：

- 建立选择接入、兼容历史插件的统一初始化和有序关闭机制。

### G1：凭据与数据安全

**时间：W2，2026-08-03～2026-08-09**

**状态：已完成（2026-07-22，提前完成）**

详细设计与验证记录：[G1-CREDENTIAL-DATA-SECURITY.md](G1-CREDENTIAL-DATA-SECURITY.md)

主要工作：

- 使用每安装随机密钥和 AES-256-GCM 加密本地 Cookie，Windows 与 Linux 共用实现。
- `credential.key` 以可见 Base64 文本保存在凭据库同一用户数据目录；明确不把“整个用户数据目录泄露”纳入本阶段防护范围。
- 不迁移旧明文状态；首次进入 G1 存储纪元时清空插件内部任务、设置、凭据、日志和临时文件。
- 从任务提交消息、任务模型和下载任务表中移除 Cookie。
- 单次任务执行开始时从当前凭据服务取得一份内存快照，不持久化到任务。
- 对日志、任务错误、附加资源摘要和持久化 URL 统一脱敏。
- 集中管理 Windows/Linux 用户数据、状态、缓存路径，并补充 Linux SQLite 原生库定位。

退出条件：

- SQLite 任务库不再包含 Cookie 字段或可复用凭据。
- Cookie 数据库只保存 AES-GCM 版本、nonce、密文和认证标签。
- 全新存储纪元不保留旧插件状态，但不删除用户已完成媒体文件和宿主 Document 文件。
- 密文被篡改、key 缺失或格式损坏时拒绝解密并回到重新登录路径。
- 日志、`error_message` 和 `extras_result_summary` 中不出现 Cookie、完整请求头或带签名参数的 URL。
- 自动化测试验证密文往返、随机 nonce、篡改拒绝、无 Cookie 列、统一脱敏和清理范围。

### G2：单任务控制内核

**时间：W3～W4，2026-08-10～2026-08-23**

主要工作：

- 为每个活动任务建立独立运行上下文和取消令牌。
- 实现单任务暂停、继续、重新开始、取消和删除。
- 实现对应的批量控制入口。
- 明确暂停、取消、重来和删除对临时文件及成品文件的不同影响。
- 修复活动任务删除、全局停止和并发数调整时的竞争问题。
- 无有效登录态时进入“等待登录”，不直接丢失任务。

退出条件：

- 暂停或删除一个活动任务不会停止其他并发任务。
- 删除活动任务前会等待网络、文件流和 ffmpeg 完全退出。
- 暂停保留断点，继续从校验通过的位置恢复。
- 重新开始会明确清理旧断点并从零执行。
- 调整并发数不会破坏正在运行的任务或导致信号量异常。

### G3：持久化与恢复闭环

**时间：W5，2026-08-24～2026-08-30**

主要工作：

- 高频进度统一节流并串行写入 SQLite。
- 阶段切换、暂停、失败、完成和删除先持久化，再通知 UI。
- 应用关闭时强制写入最后一份进度。
- 完善预期大小、实际大小、最终路径、错误类型和可重试信息。
- 精确校验 HTTP 206 和 Content-Range 起止位置、总长度。
- 恢复时以临时文件事实和完整性校验为准。

退出条件：

- 不会出现旧进度覆盖新进度或完成通知早于数据库提交。
- 视频、音频和合并阶段异常退出后均正确显示“已中断”。
- 错误 Range 响应不会生成损坏文件。
- 应用重启后不自动恢复网络请求，用户确认后才继续。

### G6：文件冲突与提交预检

**时间：W10，2026-09-28～2026-10-04**

主要工作：

- 实现跳过、覆盖、校验续传和自动序号四种冲突策略。
- 在提交前统一检查登录态、ffmpeg、输出目录、磁盘空间和文件冲突。
- 批量提交时汇总可提交、跳过、警告和阻止数量。
- 最终输出路径在提交阶段确定并持久化，避免并发任务争抢同一文件名。

退出条件：

- 不存在未经用户确认的覆盖。
- 自动序号在并发提交时仍能得到唯一且稳定的路径。
- 校验续传只接受与同一任务匹配且通过完整性检查的临时文件。
- 严重问题阻止提交，普通警告允许用户确认后继续。

### G7：ffmpeg 与错误行动入口

**时间：W11，2026-10-05～2026-10-11**

主要工作：

- 支持下载、校验和安装 Windows ffmpeg essentials 版本。
- 安装使用临时目录和原子切换，失败时保留原有可用版本。
- 支持重新检测、自定义路径和一键修复。
- 将错误分类为登录、ffmpeg、目录、磁盘、网络、CDN、资源失效、合并和未知错误。
- 为不同错误提供重新登录、安装 ffmpeg、更换目录、继续、重试或查看日志入口。

退出条件：

- 未安装 ffmpeg 的用户不需要手工修改 PATH。
- 下载包必须经过 SHA-256 校验后才能启用。
- 修复 ffmpeg 后可以只重试合并阶段。
- 用户界面中的错误信息简洁，并始终给出下一步操作。

## 6. P1：个人效率

**预计时间：W13～W30，2026-10-19～2027-02-21**

P1 的目标是从“下载单个链接”升级为“管理可以重复执行的内容来源”。

建议功能顺序：

1. 建立统一内容源接口、稳定内容标识和分页模型。
2. 支持 UP 主投稿、收藏夹、稍后再看和历史记录。
3. 支持追番追剧、订阅合集和课程。
4. 实现关键词、日期、类型筛选和跨页选择。
5. 保存完整内容源与筛选规则。
6. 实现增量检查，并区分新增、已下载、下载中、失效和规则排除。
7. 建立历史中心、文件存在性检查和脱敏导出。
8. 增加 AVC/HEVC/AV1、MP4/MKV、仅视频和仅音频控制。
9. 增加 HDR、杜比视界、Hi-Res、杜比全景声标识与选择。
10. 增加字幕语言、多格式、软字幕、弹幕 ASS/JSON 和全局/单任务限速。

P1 退出条件：

- 大型内容源可以稳定分页并保留跨页选择状态。
- 检查更新不会自动创建下载任务。
- 同一内容不会因来自不同内容源而重复下载。
- Document 重新打开后，来源、筛选、预设和输出规则保持一致。
- 输出文件的编码、容器和媒体类型与用户选择一致。

## 7. P2：专业归档

**预计时间：W31～W38，2027-02-22～2027-04-18**

P2 面向个人媒体库和长期归档场景，建议按以下顺序实施：

1. 生成 NFO、poster 和 fanart，兼容 Emby、Jellyfin、Kodi。
2. 将视频章节和番剧分集信息写入输出文件。
3. 检查历史文件、临时文件和数据库记录的一致性。
4. 预览并清理孤立临时文件、缺失成品记录和过期缓存。
5. 增加插件更新检查、版本验证和变更说明。
6. 导出脱敏日志、依赖状态和失败摘要。

P2 退出条件：

- 生成的媒体库文件可被目标媒体服务器正确识别。
- 完整性检查只报告问题，不会自动删除用户文件。
- 所有清理操作先预览、再确认、后执行。
- 更新包和 ffmpeg 包一样经过来源与完整性验证。
- 诊断包默认脱敏且不包含 Cookie、签名 URL 或完整请求头。

## 9. 每个功能组的统一完成标准

任何功能组只有同时满足以下条件，才能标记为完成：

- 功能行为符合 `PRODUCT.md` 和本路线图的边界。
- 数据结构和旧版本迁移方案已经验证。
- 关键逻辑有自动化测试，异常路径有明确覆盖。

## 11. 默认假设

- 平台目标为 Windows 与 Linux（包括国产 Linux 发行版），不包含 macOS；完整 Linux 应用适配在后续功能组继续完成。
- 产品继续作为 MyAvaloniaManagement 内部插件运行。
- P0 不增加新内容源，不实现 MKV、仅音频、主动编码选择或媒体库元数据。
- 时间估算以一名全职开发者为基准，不包含法定假期和 Bilibili API 突发变化。
- 新需求原则上进入 P1 或 P2，不在 P0 中途插入。
- 所有历史恢复、增量检查、批量删除和文件覆盖都需要用户明确确认。
- P0 结束后根据实际开发速度和 API 状态重新估算 P1/P2。
